# PHP 两项未授权远程代码执行漏洞：分析与安全自查

> **2026-10-21 更新。** [PHP 官方安全公告](https://www.php.net/archive/2026.php#2026-10-21-5)确认 CVE-2026-109618 与 CVE-2026-109619 均可导致未授权远程代码执行，并发布 8.2.35、8.3.36、8.4.27、8.5.12。两项漏洞的影响机制与不同运行方式下的验证程度有差别；下文以官方公告和对应 php-src 安全通告为准。本文不包含漏洞载荷或利用流程。

## 事件与影响范围

10 月 20 日上游先预告两项 CVSS v4.0 9.2 的严重问题；10 月 21 日正式发布四个分支的安全版本、[CVE-2026-109618 通告](https://github.com/php/php-src/security/advisories/GHSA-w8hw-w9fx-j79w)及[CVE-2026-109619 通告](https://github.com/php/php-src/security/advisories/GHSA-6wmf-4rv5-p3rp)。两项通告给出同一 CVSS v4.0 向量 `AV:N/AC:H/AT:P/PR:N/UI:N/VC:H/VI:H/VA:H/SC:N/SI:N/SA:N`。这里的评分与“任意站点可一次请求稳定利用”不是同一结论。

| 上游维护分支 | 需修复的该分支版本 | 首个修复版 | 备注 |
|---|---|---|---|
| 8.2.x | < 8.2.35 | **8.2.35** | PHP 官方称 8.2 将于 2026-12-31 结束支持 |
| 8.3.x | < 8.3.36 | **8.3.36** | 核对运行进程实际版本 |
| 8.4.x | < 8.4.27 | **8.4.27** | 核对运行进程实际版本 |
| 8.5.x | < 8.5.12 | **8.5.12** | 核对运行进程实际版本 |

表中是**PHP 上游发行版**的门槛。两个 GitHub 通告的版本字段以“< 8.2.35”等形式列出，实际判定要按 **8.2 / 8.3 / 8.4 / 8.5 各分支分别比较**，不要将 8.2.35 误判为 8.3 的修复版。预发布版、自定义编译、发行版回补包、供应商嵌入式构建及 8.6 开发分支不能只靠上游版本字符串判断，应核对其修复提交/安全公告和正在运行的二进制。PHP 8.1 及更早版本**不再获得 PHP 项目的正常安全版本**；官方额外提供 [7.4](https://github.com/php/php-src/tree/PHP-7.4-CVE-2026-109618-109619)、[8.0](https://github.com/php/php-src/tree/PHP-8.0-CVE-2026-109618-109619)、[8.1](https://github.com/php/php-src/tree/PHP-8.1-CVE-2026-109618-109619) 的最小**源码回补分支**，它们不是可直接套用的 7.4/8.0/8.1 官方发行版号。更早分支须咨询供应商并优先制定升级计划；不能因社交媒体“PHP 5 起”表述而给出 PHP 5/6 的精确受影响边界。

上游将所有服务 Web 请求的 PHP 安装列为需要关注的范围，包括 PHP-FPM、Apache mod_php、php-cgi、FrankenPHP、LiteSpeed。**风险最明确的是 mod_php**：官方称在默认 PHP 输入/内存限制及常见 prefork 多工作进程配置下，已经通过 HTTP 验证不需认证的代码执行，且 CVE-2026-109618 可在应用代码运行前触发。其他运行方式同样需要修复，但不要把这一验证结果直接推广为所有 SAPI 的相同成功率。

## 根因与利用条件（防守视角）

| 漏洞 | 官方确认的机制 | 已验证与未验证的界限 |
|---|---|---|
| **CVE-2026-109618**：OOM 期间状态损坏 | 内存不足处理可能在请求内部数据尚未完整初始化时退出当前上下文，后续请求清理错误地处理无效状态。上游补丁改变 OOM 退出方式，避免清理阶段读取该状态 | mod_php 已验证未授权 RCE，执行权限为 Web worker 账户；FPM 的源码分析支持存在风险，但通告称尚无完整 FPM 利用验证；FrankenPHP 很可能受影响，LSAPI 的应用相关路径尚未验证 |
| **CVE-2026-109619**：跨请求陈旧全局状态 | 一个请求拥有的内部状态在内存释放后仍被 worker 持有；后续请求在常规初始化重置之前读到旧状态，形成 use-after-free。补丁对跨请求状态清理做更完整的修正 | 官方验证 mod_php 与 FPM 的会话生命周期路径；PHP 8.5 的致命错误回溯路径在 mod_php 上验证 RCE。需存在产生旧状态与后续消费旧状态的可达条件；同一 worker 处理相关请求，不能泛化为所有配置都能稳定利用 |

这两项可使攻击者以 **Web worker 的权限**执行代码；能否访问应用源码、数据库凭据、云密钥或横向目标取决于实际权限及隔离。没有证据表明“获得 root”是漏洞的默认结果。[8.5.12 ChangeLog](https://www.php.net/ChangeLog-8.php#8.5.12)在 Core 项下将两项通告列为修复，其他安全修复条目不能与这两个 CVE 混为一谈。

## 安全自查与处置

1. **明确运行版本。** 逐项列出入口、服务、节点/容器、PHP SAPI、实际 worker 路径与版本、供应商包/镜像来源、配置覆盖和公网可达性。不要使用另一套 CLI PHP 的 `php -v`、Composer 依赖或 Web banner 代替运行进程证据。对四个上游维护分支逐支比较修复门槛；发行版回补要保存厂商公告和包修订号。
2. **优先升级。** 首先安排公网 mod_php，再处理其他对外 PHP 服务及可被不可信请求触及的内网服务。升级到对应分支修复版或含经验证回补的供应商包，完成兼容性、备份/回滚、所有 worker 重启和多节点版本复核。PHP 8.1 及更早版本优先迁移至受支持分支；若临时回补源码，应由维护团队核对补丁和构建来源。
3. **无法立即升级时缩小暴露。** 控制对外访问，审查上传/输入大小与请求数量限制。上游提出的 `memory_limit=-1` 仅能减少 CVE-2026-109618 的可控 PHP 限额触发路径，可能增加资源耗尽风险，且底层分配失败仍可触发问题；需评估资源隔离与业务稳定性。`session.upload_progress.enabled=0`（所有分支）及 PHP 8.5 的 `fatal_error_backtraces=0` 可减少 CVE-2026-109619 的已证实路径，必须在足够早的配置层生效并重启所有 worker；这些设置**均不等于修复**。上游明确只有安装修复才是完整处置。
4. **调查已有线索。** 关联代理/HTTP 请求、PHP/FPM/Apache 错误与致命异常、内存耗尽、worker 重启、会话上传设置、PHP worker 异常子进程、外联和文件变更。上游建议调查请求初始化前的诊断及应用可达的致命错误；单条日志、单次内存告警或“未见子进程”都不能证明漏洞利用或未利用。现阶段没有可依赖的通用请求特征或官方 IOC，尤其不要将 Huntress 文中其他 PHP 入侵案例当成本事件证据。
5. **若多源证据支持失陷。** 先隔离与保全，再按响应流程核查持久化、应用代码及可达凭据，决定重建和轮换范围；升级能阻止后续利用，但不能自动清除既有入侵。
